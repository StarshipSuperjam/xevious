# Release fidelity — the last gameplay, art and HUD corrections before the release candidate

- Mechanic: Slice 21, the one release pull request. Each numbered item below is one focused commit. (1) **AREA-02, `area.add-object-dispatch`:** the area schedule's 13 add_object records now place their objects. The hidden bonus flag appears in areas 1, 3, 5 and 7 without the debug key; a Torkan appears in area 3, a Kapi in area 7, a Terrazi in areas 7 and 11, and the Garu Zakato in areas 9, 10 and 14. A record whose slot is already busy is dropped: the arcade writes the type into the slot, but a live object never reads it and clears it when it is freed, so nothing is queued. The Garu Zakato now lives in arcade object slot 0x3B, so its detonation writes into the four slots after it (0x3C–0x3F), as the arcade does: a free slot gets a Brag Spario, and a slot already holding an enemy only has that enemy moved onto the Garu with the Spario's velocity. (2) **PLY-02 / AREA-01, #158 — the world keeps running through the player's explosion.** A hit no longer freezes the screen: the craft explodes in place while the terrain, enemies, bullets and spawners carry on for the arcade's 88 frames, and only then does the death route (respawn, game over or the end of a demo) run. (3) **PLY-02.forest-wait, `player.final-forest-wait`.** After the last craft is lost, the screen shows only forest for 64 frames before the high-score entry, GAME OVER or the other player's turn, as after every arcade death. (4) **DIF-02.ship-divisor, `difficulty.ship-number-divisor`.** The area schedule's score re-tune divides the player's score by the ship number — the craft in play, counted from 1 — instead of the craft left, so a player who scores well while losing few craft meets more pressure and one who has lost many is spared, as in the arcade. (5) **ECO-03.stop-after-two, `economy.stop-after-two` (#103).** The second bonus craft comes at 60,000 points, not 80,000, and the ones after it at every 60,000 (120,000, 180,000 …). Past 9,960,000 the threshold wraps back to 20,000, as the arcade's does, so the next awards grant craft again. The setting that stops after the second bonus craft is recorded as unreachable in this build. (6) **AIR-10.brag-spario-survives, `presentation.reference-art`.** A shot never destroys a Brag Spario. Each hit scores 500 and uses up the shot, and the Spario keeps homing in; it leaves only off the screen. Until this commit the port blew it up with the shared air explosion.
- Derived behavior: (1) **add_object.** When the area clock reaches an add_object record's row, the record names an object type and one raw arcade object slot: 0x00 for the bonus flag (the ground band's slot 0), 0x3A or 0x3B for the single flyers (the first two formation slots). The arcade writes the type into that slot unconditionally; on the same frame the object pass gives the type its handler only if the slot was idle. If the slot was busy, the live object's handler keeps running and clears the type when that object frees, so the record is lost — never queued or retried. The new object's own init runs on the following frame: the flag takes the craft-excluding random column, hidden and worth 1,000 at reveal; Torkan, Kapi and Garu Zakato take the plain random column; Terrazi takes the craft-excluding one. Because the object pass runs before the formation spawner, a placed single owns its slot before the spawner writes; the spawner writes a type into the first formation slots from 0x3A every frame, idle or not, but a live object ignores it, so the single keeps its slot until it is freed. The Garu Zakato's detonation reads slot 0x3B absolutely and writes the Garu's position and the four Spario velocities into 0x3C–0x3F; only the free ones become Brag Sparios. (2) **The explosion window.** On a hit the flight sound stops and, in a real game only, the explosion sound starts; an attract demo dies silently. The craft's own handler switches to the explosion: seven 8-frame steps, then a 32-frame pause in which the craft is no longer drawn — 88 frames in all. Nothing else stops: the objects, the scroll, the spawners and the enemy bullets are gated only on the scroll being disabled, and that happens only at the window's end, together with the ship number going up. During the window the craft cannot be hit again (the hit test runs only on the live craft's path), cannot move or fire a new shot, no new bomb press is accepted, and the crosshair stays where it was; shots already flying keep moving and scoring, and a bomb already falling keeps falling and scores where it lands, because the bomb is a coroutine that resumes past the press check. The bonus flag's collection test reads the craft's shadow position without asking whether it is exploding, so the craft can collect the flag while its explosion is drawn. In the pause its state is cleared, and the shadow update then zeroes its position: the Amiga layer also parks its shadow off-screen, so it can no longer collect the flag (the Neo Geo layer zeroes the position but leaves the shadow where it was). For those 16 ticks every aim, homing turn and spawn position that reads the craft's position reads 0. When the window ends an attract demo ends; a real game runs the existing death route. The near-end checkpoint then reads the live scroll row (record 015). (3) **The forest wait.** After every real-game death the arcade fills the background with forest and waits 64 frames, and only then looks at the craft left: it continues with the next life, or the game ends (the best-five check, then GAME OVER), or in a two-player game the turn passes. The scroll counter is not moved, so the checkpoint still reads the death row. On the frame the scroll is disabled the object pass starts over, which clears the whole 64-object table, and then idles until the scroll is enabled again; so every enemy, bullet, ground object and the bomb sight vanish as the wait begins, and the wait shows only forest and the score display. A demo ends when the scroll is disabled and never reaches the wait. (4) **The ship number.** Each player has a ship number: 1 when the game starts (both players in a two-player game), one more, as a byte, when each death's 88-frame window ends — an attract demo's included — and swapped with the other player's at the turn change. The re-tune record takes the score's thousands as its four BCD digits read as one binary number (20,000 points is 0x0020 = 32; 999,000 is 0x0999 = 2,457) and divides it by the ship number with the floor. A ship number of 0 — reached only after 255 craft — makes the arcade's loop return 0xFFFF. The quotient is capped at 16 by a signed compare, so a quotient of 0x8000 or more (from 8,000,000 points while still on ship number 1) is not capped. The result is added to the AI level within the byte, with no fold. The level raise likewise adds within the byte before its fold test. (5) **The bonus threshold.** When the score reaches the threshold, a craft is granted and the threshold advances. If the threshold just reached is below the setting's increment, the new threshold is the increment itself; otherwise the increment is added. At the default setting (first 20,000, increment 60,000) that gives 20,000, 60,000, 120,000, 180,000 …. The add is a four-digit BCD add of the thousands that drops its carry, so 9,960,000 + 60,000 becomes 20,000; that wrapped threshold is below the score, so every award grants a craft until the threshold climbs back past it. On the add path only, the arcade first checks the low three bits of the inverted DIP switch byte; the value 6 marks the last bonus, so the craft just granted is the last one. The catch-up path skips that check. The bonus setting itself is bits 2–4 of the same byte, so only bit 2 is shared: the value 6 needs an odd setting index and also bits 0–1 set to 1,0 from the neighbouring switch field, so it is not a bonus setting on its own. (6) **The Brag Spario under fire.** Its handler has no hit branch: it sets `_STATE` back to 2 every frame before it moves. The shot test hits only an enemy whose `_STATE` is 2; a hit sets 3, clears the shot, scores the enemy's points (500 for a Brag) and plays the flying-hit sound. The hit leaves `_CODE` alone, so the body is drawn throughout. Both collision tests read the sprite positions the sub CPU snapshots at the start of each frame, before the object pass moves anything, so a shot meets the Spario where it is drawn; the next frame its handler puts it back to 2. The craft-contact test runs before the handler and skips any enemy not in state 2, so on the frame after a hit the Spario cannot ram the craft. During play it is freed only when it leaves the screen. Its only spawner is the Garu Zakato detonation: type 0x09 is in neither flying-type table and in no schedule record.

- Scratch interpretation: **A one-tick register, then a placement step.** The schedule consumer's add_object branch checks the target's `slot type` at the moment the record fires — the arcade's pickup point — and, only if it is 0, writes `pending object type` and `pending object slot` (the raw slot plus one, the 1-based Scratch index). A busy slot leaves the register empty: the record is gone. The walk then calls the new warp proc `place pending object` after the walk and the bomb and before `spawn flying enemies`; it re-checks the slot is still empty, stamps the type through `walk type`, runs that type's EXISTING init (`INIT_TORKAN`, `INIT_KAPI`, `INIT_TERRAZI`, `INIT_GARU_ZAKATO`, or the flag seed now shared with the debug ground key), and clears the register every time. The flag seed was factored out of the debug-key path into one builder with no debug-key gate. A build guard (`_check_add_object_records`) refuses a schedule that names a type/slot the step cannot place, or two add_object records on one row in one area (the register holds one record per tick). `GARU_ZAKATO_SLOT` is now the second flying slot (0x3B); the debug Garu stamp uses it too. (2) **A walk-owned window.** The game stays in `playing`. Two Stage variables, `dying` and `dying tick`, carry the window; the walk's death check, on a hit, clears `player hit`, sets `dying` = 1 and `dying tick` = 0, runs the shared stop-all, raises `sfx death` when not in attract, and sends `death draw`. Each later tick a `dying` step counts `dying tick` up, sends `death draw`, and at `dying tick` > 43 runs the real-or-demo branch that used to follow the hit (the demo ends; a real game raises `keep sounds`, so the death cue started at the hit survives the transition's stop-all, then spends the craft and runs the `player-dead` transition). The `solv_death` renderer keeps no clock: its `death draw` receiver draws the explosion frame picked from `dying tick` while `dying tick` < 28 and hides otherwise; its `player-dead` entry is now only the epoch check and `death complete`. `dying` is tested **inside** the two shared overlap reporters (`_craft_overlap_reporter`, `_bacura_fair_craft_reporter`), so nothing can raise `player hit` during the window; the flag's collection uses the reporter with the narrower `drawn` gate (`dying tick` < 28) instead. In the pause (`dying tick` ≥ 28) `read player` reports the craft at 0 (slot x, slot y, row and column) instead of reading the hidden sprite, as the arcade's zeroed `_X`/`_Y` do. The craft sprite hides, and the blaster's advance/fire/release, the bomb arm, the crosshair tracking and the attract pilot are each gated on `dying` = 0; shots and bombs already in flight are not. The music loop stops while `dying`. Every director reset clears `dying`, `dying tick` and `player hit`; neither is a per-player field. (3) **A paced hold in `player-dead`.** The death sprite's `player-dead` entry, when `craft` = 0, sets the two terrain strips straight to the re-top's terrain state (the forest filler alone on screen) and sends `terrain draw`, then holds `FOREST_WAIT_TICKS` (32) paced frames — the walk is off in `player-dead`, so a paced hold is safe there — and only then runs its epoch-checked `death complete`, so a superseding transition during the hold still drops the hand-off. The area clock is not touched, because the two-player handoff's checkpoint reads it afterwards. The field is already empty by then: the transition into `player-dead`, like every director transition, sends `director stop` (every object renderer stops drawing) and `director reset`, whose Stage receiver runs `clear slots` on every scope, freeing all 64 slots — the port's counterpart of the arcade's object-table clear, after every death. After a death with craft left the port keeps its READY hold in place of the wait (record 055 deviation 10), so the extra hold is only for the last death. (4) **A fifteenth per-player field.** `ship number` and `other ship number` join `PLAYER_CONTEXT_FIELDS` (now 15), so the existing new-game copy and turn-change swap carry them. The new-game reset sets `ship number` to 1; the `dying` step's window end sets it to `(ship number + 1) mod 256` before the real-or-demo branch, so a demo death counts too, as the arcade's does; but every demo, like every game, starts through the new-game reset, so a demo's count is never read (deviation 8). The re-tune branch of `_consume_schedule` builds `ai adjust` as d0 + 16·d1 + 256·d2 + 4096·d3, each `d` being one decimal digit of the score's thousands — the BCD word read as binary — then, if `ship number` = 0, sets it to 65535, else to `floor(ai adjust / ship number)`; a single `if` caps it at 16 only when it is above 16 and below 32768, the signed compare's escape; and `ai level` becomes `(ai level + ai adjust) mod 256`. The raise is now `(ai level + increment) mod 256` before its fold. The Scratch floor of a positive quotient equals the arcade loop's result for every byte divisor and BCD dividend; a unit fixture checks that. (5) **An if/else in the advance.** `check bonus life`'s grant arm now ends in an if/else on `next bonus < increment` (the increment read from `repeat bonus 123` at the fixed bonus index). The stop-after-two flag is not built: at the fixed bonus index 0 the inverted DIP's bit 2 is clear, so the raw value can never be 6. The extracted `scores.json` note for the increments still reads "points added to the threshold after each award"; it comes from the guarded extractor, so the advance rule is stated in the spec and here instead.
