# High-score table and ten-character initials entry — the live best-five and the name-entry screen

- Mechanic: CAB-04 (high-score table and initials) — the best-five high-score table is **live**: a qualifying end-of-game score ranks into the five-entry table and the player enters a **ten-character** name from a 27-symbol set (A–Z and space), after which control returns to the attract cycle. This completes the cabinet flow begun in slices 17–18, turning the previously cosmetic pre-baked best-five display into a table that reflects scores earned this session, and is routed to by the ECO-04 game-over verdict ([014](014-game-over.md)).
- Derived behavior: The table holds five entries, each a score and a ten-character name; at boot the RAM table is seeded from ROM defaults and the attract loop renders the **live RAM table**, not the ROM defaults. When a game ends, the final score is copied into a working "entry 0" buffer with a blank (all-space) name and compared against the five entries from the most-significant score byte down; the first entry the new score is **not below** (a tie places) is the insertion rank — that entry and every lower one shift down by one slot (the old fifth entry drops off) and the new score is written at the rank with a blank name. A score that beats none of the five (insertion index 5) does not place and the game ends without entry. On a placement the player types the name in place into that rank's slot: the letter under the cursor cycles through the 27-symbol ring (A → … → Z → space → A, wrapping both directions), a commit stores the current letter and advances the cursor to the next of ten cells, and entry finishes when the tenth cell is committed **or** a fixed countdown (seeded once at entry start, decremented unconditionally regardless of input) expires and commits whatever was entered so far. Entry is forward-only — there is no cursor-back or rubout. In a two-player game each player independently reaches the high-score check at their own game-over. Persistence is platform-dependent: with no on-screen-display store the table is simply the ROM defaults each boot.
- Reference provenance: `jotd666/xevious@71473685a8c7856c8401c8519276cd97a38d4183`; citations are `src/xevious_main.68k` unless noted. `init_high_score_table` (1565-1576) copies the ROM default table (0x50 = 80 bytes = five 16-byte entries) into RAM and the three-byte displayed high score from `ROM_high_score`; `display_high_score_table` (1475-1542) renders the live RAM table as five rank/score/name rows (each name ten characters). `check_for_high_score` (1618-1655) copies the player score into the "entry 0" buffer, blanks the name buffer with the space code 0x24, and walks the five entries most-significant byte first — a strictly lower score branches out and a higher one branches to the shift, while at the least-significant byte a tie falls through to the shift and **places** (1653-1656), which is the `>=` placement rule. `move_high_score_entry_down` (1656-1665) shifts an entry and each lower one down by sixteen bytes; `score_lower_than_entry` (1667-1704) computes the insertion index, ends the game if it is 5 (did not place), otherwise writes the new entry and arms name entry — `move.b #10,(name_entry_char_cnt)` sets ten characters (1700) and `move.b #0x80,(countdown_timer_1)` seeds the timer once (1701). The name-entry ring is `name_entry_inc_char` (1773-1781, wraps space→'A') and `name_entry_dec_char` (1736-1744, wraps 'A'→space); `name_entry_append_char` (1746-1756) stores the current letter and advances the pointer, falling into `name_entry_finished` (1757-1769) at the tenth; the timer decrement and its finish branch are at (1727-1728). The five default scores (40,000 down to 20,000) are committed, BCD-decoded, in [docs/spec/data/scores.json](../spec/data/scores.json) (`high_score_defaults`). Two-player per-player entry at each player's own game-over is `game_over` (549-563). The settled spec is [cabinet flow](../spec/cabinet-flow.md) (CAB-04) and [scoring, lives, and game over](../spec/scoring-lives-and-game-over.md) (ECO-04).

- Scratch interpretation: The scores list `high score table` (`HIGH_SCORE_TABLE_ID`, five numbers, item 5 the fifth-place cutoff already read for the `qualified` verdict) gains a parallel names list `high score names` (`HIGH_SCORE_NAMES_ID`, five strings) seeded from the existing `ATTRACT_DEFAULT_INITIALS` placeholders, so a project **reload** restores defaults (the storage-free equivalent of a power cycle) while a bare green flag does not disturb a within-session table. A `rank in` Stage warp proc walks ranks 5→1, finds the smallest rank the `entry score` is **not below** (`>=`, encoded as `not(entry score < rank score)`) using one loop-scratch register `rank cursor`, shifts **both** lists down in lockstep from the bottom, and inserts the score with a blank name at `entry row` (0 means it did not place); the entry screen later writes the typed name into `high score names`[`entry row`] in place, faithful to the arcade's `name_entry_ptr`. Numeric comparison replaces the reference's three-byte BCD compare (observationally equivalent). Because Scratch has no runtime text compositor, the live table and the in-progress name are drawn with **per-glyph clones** on the `start_screen` target — the HUD score-digit idiom — in three new cell roles: a rank digit (`ATTRACT_ROLE_TABLE_RANK`, digit-of-number over the row index), a name letter (`ATTRACT_ROLE_TABLE_NAME`, the new **letter-of-string** reader over `high score names`), and a score digit (`ATTRACT_ROLE_TABLE_SCORE`, digit-of-number over `high score table`), laid out five rows deep at the `hud_glyphs.SMALL_TEXT_GEOM` monospace pitch so ten-character names fit the 480-wide stage; the single pre-baked `best-five` costume (old role 4) is removed and `attract-scores` now renders the two live lists. The new `high-score-entry` `game state` adds `game-over -> high-score-entry` (qualifying) and `high-score-entry -> title` (done) edges, plus a `high-score-entry -> high-score-entry` self-edge used to re-arm the screen for a second qualifying player. Its machinery vars (all Stage-owned, in `director_variable_ids` so sprites cannot write them while the display may read them) are `entry char` (0..25 = A..Z, 26 = space — the 27-ring index), `name buffer` (a STRING the compositor reads a letter at a time, never a Stage-list surface), `entry cell` (0..9 cursor/count), `entry row`, `entry player` (the 2P tag), `entry recheck` (a one-shot the routing arms), `entry score`, and `rank cursor`. Input hats gated `if_state("high-score-entry")` (so they do not collide with the title selector or play movement) map **up/down** to cycling `entry char` with wrap and **Space** to appending letter (`entry char` + 1) of the ring to `name buffer`, advancing `entry cell`, resetting `entry char`, and finishing at the tenth cell; a total-countdown hold finishes on timeout. The active cell is marked by the slice-18 ghost-pulse (no new cursor glyph); `CONGRATULATIONS` / `ENTER YOUR INITIALS` headers and a `PLAYER n` tag render as static sheet-text. The `game over complete` receiver computes the `>=` verdict and, for a qualifying current player, seeds `entry score`/`entry player`/`entry row` (via `rank in`), arms `entry recheck` to `two player`, and transitions into the entry state; `_high_score_finish` writes the name, then (when `entry recheck` is set) re-checks the other player against the now-updated fifth place and re-arms the screen through the self-edge, otherwise raises `attract` and returns to `title`/`cold-start`. Finally, a coherence fix seeds the displayed `high score` scalar from `high score table` item 1 at cold-start (not a fixed constant), so the HUD high score equals the table top and both reflect a within-session top score.

- Known deviations or uncertainty: (1) **Two-player entry order (divergence).** The arcade enters each player at their own game-over (first-to-die first); the port collapses game-over at the final both-out point (as slice 18 already does) and enters them **batched current-then-other** (last-to-die first), recomputing the fifth-place cutoff between them via the one-shot `entry recheck` and the `high-score-entry -> high-score-entry` self-edge. Both players still land in their correct ranks — the ordering differs, the result does not. (2) **Numeric vs BCD compare.** `rank in` compares scores as Scratch numbers, not the reference's three-byte BCD bytes; observationally equivalent over the value range, so no separate record is warranted. (3) **Persistence model.** The reference's high-score I/O is on-screen-display/platform-dependent (`OPT_ENABLE_HIGH_SCORE_IO`); absent a store the arcade shows ROM defaults each boot. The port is faithful to the storage-free case: the table persists **within a session** (a ranked-in score shows in attract and can be beaten) and a **project reload** restores the committed defaults — this is a reload, not a bare green flag, and the two lists are intentionally **not** reset at cold-start (commented at their declaration so a maintainer does not fold them into `clear slots`). (4) **Total-timeout (medium confidence).** The finish countdown is a fixed total seeded once at entry start (`countdown_timer_1` 0x80, ~68 s) and decremented unconditionally — it is **not** an idle timeout; no input path resets it. The exact real-time duration depends on the decrement cadence and is recorded as medium confidence. (5) **HUD high-score = table-top (coherence decision).** The displayed `high score` is seeded from `high score table` item 1 at cold-start rather than a fixed constant; by construction both defaults are 40,000, and within a session the HUD high score tracks the table top — an operator-approved faithful reading of `init_high_score_table` (1565-1576), which seeds both from ROM together. (6) **Control remap (port necessity already recorded).** The arcade cycled letters with the joystick left/right and committed with the fire button; the port uses up/down + Space for consistency with the title 1P/2P selector, a deliberate remap recorded in the locked control-mapping spec (`docs/spec/core-game-systems.md`, slice-19 PR-1 `guardrail-ack`). (7) **Blank/space cell.** The font sheet has no space glyph, so a space in a name renders as a blank advance (no costume), not a drawn character. (8) **Entry-screen wording** (`CONGRATULATIONS`, `ENTER YOUR INITIALS`, `PLAYER 1`/`PLAYER 2`) is project-original text pending the operator's playtest confirmation, like the rest of the cabinet HUD layout.
