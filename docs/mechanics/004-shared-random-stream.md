# Shared pseudo-random stream

- Mechanic: One deterministic 16-bit pseudo-random stream every stochastic behavior will draw from (SYS-04).
- Derived behavior: A single shared seed advances by the reference's generator rule; each advance returns one byte and updates the state, so seeded runs repeat exactly.
- Reference provenance: `jotd666/xevious@71473685a8c7856c8401c8519276cd97a38d4183`; `src/xevious_main.68k`: `pseudo_random_gen` (1428-1445), direction variant `gen_rnd_dir` (2156-2165). The update rule and its five golden fixture sequences are the normative record in [docs/spec/data/rng.json](../spec/data/rng.json) (generated by `tools/reference_extract.py`, `rng_step`) and described by [core game systems](../spec/core-game-systems.md) (SYS-04); this record cites that home and does not restate the arithmetic.
- Transfer class: General behavior and numeric constant (instruction-derived rule; no source text or media copied).
- Scratch interpretation: The Stage owns `rng state` (the shared 16-bit seed) and `rng out` (its latest output byte), advanced by a warp (run-without-screen-refresh, atomic) `rng step` custom block. Because Scratch custom blocks have no local variables, the four per-step working values (`rng high`, `rng new low`, `rng new high`, `rng extend`) are Stage variables too — machinery, not director state. The rule uses only mod/floor/multiply/add blocks (Scratch has no bitwise operators): the low byte's wrap carry is `1` when the new low byte is `0`, then forced to `1` when the high byte's bits 7 and 2 are equal. The centralized-ordered-update decision that keeps consumer draw order is recorded in [core game systems](../spec/core-game-systems.md); its walk lands with the entity slices in this same build.
- Scratch evidence: Stage variables `rng state`, `rng out`, `rng high`, `rng new low`, `rng new high`, `rng extend`; the `rng step` warp custom block in `tools/game_director.py` (`install_rng_step`); the cold-start / new-game seed in the Stage `director reset` receiver; the golden interpreter test and its negative fixture in `tests/test_spec_docs.py` (`GeneratedRngStep`), which runs the *emitted* block graph against the five committed fixtures.
- Acceptance criteria: The generated `rng step` block graph, interpreted directly, reproduces each of the five golden sequences in [docs/spec/data/rng.json](../spec/data/rng.json) (256 outputs and the final state per seed), and the negative fixture proves the check reddens when an operand is corrupted; two clean builds stay byte-identical and survive the build→import round-trip.
- Fidelity status: **Dormant machinery, foundation-only.** The stream is built and verified against the golden data, but no behavior draws from it this slice — every consumer (aerial enemies, Bacura, enemy bullets, difficulty, formations) arrives with a later slice. The rule itself is reference-faithful (golden-verified); only its *consumption* is unbuilt. Pulled forward into this slice from its BUILD_PLAN slice-7 home per issue #14's scope.
- License status: The pinned reference repository states no reusable license; no reference source text or media was copied — the rule is instruction-derived and the golden data is a derived transcription.
- Known deviations or uncertainty: The cold-start seed value (`0x4A39`) is a **project-defined placeholder** with no reference basis — the spec records no arcade power-on seed yet; it only fixes repeatability and no consumer reads it this slice. Its "seeded runs repeat exactly" acceptance is structural now (the seeding path exists and the rule is deterministic); the operator-observable half is deferred to the first slice with a live consumer. The `gen_rnd_dir` direction variant is recorded in the reference but not built until a consumer needs it.
