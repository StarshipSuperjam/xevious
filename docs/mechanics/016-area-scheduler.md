# Area object scheduler — the ordered schedule consume and its lossless representation

- Mechanic: AREA-02 (partial, foundation) — each area's object schedule is consumed strictly in order by the area clock: a record fires once when the scroll row reaches its trigger row, then the cursor advances. This slice ingests one fixture area (area 1) into a lossless, slice-6-ready representation with an EMPTY per-record dispatch seam.
- Derived behavior: While an area scrolls, its schedule is walked in table order — each record waits until the scroll row equals its trigger row, then executes and the cursor moves to the next. Every area table ends with a sentinel row that never fires, because the area completes at row 0x0E before the sentinel's row (0x0D) could recur. A new life or a fresh area re-points the cursor at the area's first record. The records' effects (spawn a ground object, set/reset a flying formation, raise difficulty, set a fire-permission mask, control Bacura/Sheonite/Andor) arrive with the enemy slices; the scheduler that orders and dispatches them is this mechanic.

The 16 decoded schedule tables (this slice ingests area 1) are committed in [docs/spec/data/area-schedules.json](../spec/data/area-schedules.json), hash-guarded by [manifest.json](../spec/data/manifest.json); the ordering and sentinel rule are the settled [area progression and terrain](../spec/area-progression-and-terrain.md) document.
- Transfer class: General behavior and structured table.
- Scratch interpretation: Area 1's schedule is ingested by parsing the committed JSON at generation time into three FAITHFUL parallel Stage lists — `schedule handler` (the record kind), `schedule trigger row` (the scalar the consume compares), and `schedule payload` (an OPAQUE JSON serialization of `object_type` + the record's variable `params`) — so no handler's parameters are dropped and the schema never has to grow (slice 8 decodes the payload; it adds no column). The scalar `end_sentinel` is MATERIALIZED as the terminal row (handler `sentinel`, trigger 0x0D), so the table is self-terminating and the extractor's "every table decodes to its sentinel" invariant is reproduced (53 records + sentinel = 54). Two 16-entry index lists, `area schedule start` and `area schedule end`, are the slice-6 seam: every area maps to area 1's table this slice ({1, 54}); slice 6 rewrites only their data and appends areas 2–16 to the same columns, moving no code. The ordered consume is the `else` arm of the area clock's completion `if/else` (so completion and consume never both run on a tick): a `repeat until` loop that stops when the cursor passes the area's end index OR the record's trigger row no longer equals the current scroll row, advancing `schedule cursor` and the observable `schedule fired` each pass. Fire-once is guaranteed by the monotonic cursor over the monotonic progress; the sentinel never fires because the dispatch reads the POST-increment row, which is <= 12 until the wrap and never the area-top row 0x0D. The per-record handler dispatch is an EMPTY seam this slice, mirroring `advance slots`.

- Acceptance criteria: The ingested columns round-trip losslessly from `area-schedules.json` area 1, with the sentinel materialized and the index lists mapping every area to it (engine, golden). The consume loop advances the cursor and the fire counter, dispatches nothing per record yet, and stops at the sentinel/end bound (engine, structural). In real play the schedule consumes records once, in row order, as the clock advances (engine, scratch-vm harness). Operator: with the `schedule fired` variable watcher open during play, the counter climbs as the area scrolls (once per record) and resets at each area boundary — an inspectable confirmation, no on-screen readout this slice.
