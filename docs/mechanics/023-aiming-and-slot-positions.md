# Homing-aim tables and per-slot position fields

- Mechanic: The shared 32-direction homing-aim system (the octant quantizer plus the per-tier velocity tables) and the per-slot position/motion fields every live entity needs — the dormant foundation the Toroid vertical slice consumes (AIR-01, AIR-12, SYS-02 position authoring).
- Derived behavior: A homing entity aims at the craft by quantizing the vector from itself to the craft into one of 32 directions and copying that direction's fixed velocity pair; index 0 is pure scroll-axis motion. Each object slot carries a scroll-axis and lateral position (16-bit, 1/32-px), a velocity pair, an animation timer, a sprite code, its score's value-table position, and a per-type sub-state. No entity reads or writes these this commit — the tables are baked and the fields are zeroed; the aim procedure and the first author (the Toroid spawner/updater) land in the next commit.
- Reference provenance: `jotd666/xevious@71473685a8c7856c8401c8519276cd97a38d4183`; the four `angle_dX_dY_*_tbl` velocity tables (`src/xevious_main.68k` 6290–6427) and the `octant_angle_tbl` quantizer (1418–1420) are decoded into [docs/spec/data/aiming.json](../spec/data/aiming.json) by `tools/reference_extract.py` (`decode_aiming`), verified against the hash manifest at load. The byte order is the reference's own: each table pair is (dY, dX) per `cpy_dY_dX_to_obj` (3383) — the label reads "dX_dY" but the consumer copies the first byte to `_dY` (lateral velocity) and the second to `_dX` (scroll-axis velocity); the extractor records this so the columns bind to the axes the reference actually uses. The 64/48/32/24 magnitudes are the four speed tiers (4 / 3 / 2 / 1.5 px/frame after the reference's ×2 apply). The slot ranges and the shadow-unit hit windows are the recorded values in [player craft and weapons](../spec/player-craft-and-weapons.md) and [core game systems](../spec/core-game-systems.md); this record cites those homes and does not restate them.
- Transfer class: Numeric constant and structured lookup table (instruction-derived structure; the velocity/quantizer tables and slot-field layout are derived data and a port mapping — no source text or media copied).
- Scratch interpretation: `aiming.json` is baked into read-only Stage lists — the 33-entry `octant table` and, for this slice, the two tiers Toroid uses: `aim dy 24`/`aim dx 24` (its 1.5 px/frame approach) and `aim dy 32`/`aim dx 32` (its aimed bullet at 2 px/frame), each a direction's (dy, dx) split into two parallel 32-entry lists. The eight per-slot fields are parallel 64-entry Stage lists beside `slot type`/`slot state` — `slot x`/`slot y` (scroll/lateral position in 1/32-px), `slot dx`/`slot dy` (velocity), `slot timer`, `slot code`, `slot pts` (1-based `value table` position, so the single-hit path scores type-agnostically), and `slot flag` (per-type sub-state). All are cleared to zero by `clear slots` on every reset. Gameplay stays in these arcade units; the port scale is applied only at the renderer and the one read of the player's live position, both in the next commit.
- Scratch evidence: the baked lists `octant table`, `aim dy 24`, `aim dx 24`, `aim dy 32`, `aim dx 32` and the eight `slot *` field lists in `expected_project`; `SLOT_FIELD_LISTS`, `_load_aiming_tables`, and the `AIM_*`/`OCTANT_TABLE`/`SLOT_*` constants in `tools/game_director.py`; the extended `clear slots` warp block; the model fixtures `AimingTables` (angle tables vs the sine/cosine model, octant monotonicity, baked lists vs `aiming.json`) in `tests/test_spec_docs.py`; the extended `_sys02_slot_failures` (every slot field zeroed at generation; `clear slots` covers every slot list) and its negative fixtures in `tests/test_scratch_project.py`; the `aiming.json` digest pin in `docs/spec/data/manifest.json`.
- Acceptance criteria: `aiming.json` re-derives byte-identically from the pinned reference and matches its manifest digest; every angle-table entry equals its sine/cosine model within one unit; the octant table is a 33-entry non-decreasing quantizer spanning 0..0x40; the baked Stage lists equal the committed data; every `slot *` list is length 64 and all-zero at generation and is re-zeroed by `clear slots`; the negative fixtures redden when a field is dirtied or dropped from the clear; two clean builds stay byte-identical and survive the build→import round-trip. The in-play half — enemies aiming and moving — is the next commit's, exercised in the harness and the operator playtest.
- Fidelity status: **Dormant data / recorded tables, foundation-only.** The aim tables and slot fields are baked and zeroed; no entity aims, moves, or occupies a slot yet. The aim procedure, the formation spawner, and the Toroid updater that author these fields land in the next commit of this slice; their live proof (a Toroid aiming, moving, and being drawn) is the harness scenario and the operator playtest there.
- License status: The pinned reference repository states no reusable license; no reference source text or media was copied — the aim tables and slot-field layout are instruction-derived and the values are a derived transcription.
- Known deviations or uncertainty: (1) The angle-table byte order is (dY, dX) despite the `angle_dX_dY_*_tbl` label; recorded here and in the extractor, sourced to `cpy_dY_dX_to_obj`, so the axis binding is unambiguous. (2) Only the 24- and 32-magnitude tiers are baked this slice (the two Toroid uses); the 48- and 64-magnitude tiers are proven in `aiming.json` and its model fixture but not yet baked, and land with the families that use them (slices 10–11). (3) The sine/cosine comparison is a documented cross-check, not the source of truth — the reference table is authoritative; a ±1 tolerance covers the reference's own integer rounding.
