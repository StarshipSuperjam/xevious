# HUD render — score, high score, and remaining-craft readouts

- Mechanic: ECO-02 HUD render — the on-screen score, running high score, and remaining-craft (lives) readouts, built from the digit/letter glyph and life-icon costumes ECO-02's media commit (010) attached to the hidden `hud` sprite.
- Derived behavior: While the HUD is visible (any state but the title screen or boot), the score and high score are shown as 7-digit, leading-zero readouts *(leading zeros blanked in slice 21, [record 056](056-release-fidelity.md) item 11)* that track their Stage variables tick by tick, a static "HIGH SCORE" label sits above the high-score group, a flashing "1UP" label sits above the score group, and one ship icon appears per remaining craft, rebuilt whenever a bonus life is granted. The HUD only ever reads `score`, `high score`, and `craft`; it never writes them.
- Reference provenance: The arcade HUD layout and glyph set are described in the settled [scoring, lives, and game over](../spec/scoring-lives-and-game-over.md) document (ECO-02) and the credited HUD font sheet ingested in `assets/hud-font/manifest.json` (see docs/mechanics/010). No new reference source is transferred this commit; this is the rendering of state already recorded by ECO-01/ECO-03 (docs/mechanics/009, 011) through the glyph media docs/mechanics/010 ingested.
- Transfer class: General behavior (display logic only; no new numeric or table data).
- Scratch interpretation: The `hud` sprite stays hidden and only spawns clones, tagged by a sprite-local `hud role` (and, for digit clones, a `hud place`) snapshotted at creation — the same idiom the blaster clone uses for its allocated shot slot. Clones are cleared on every `director stop` (the existing `clones=True` common-stop pattern) and respawned on `director enter` whenever the state is HUD-visible; because `director stop` always precedes `director enter` on every transition, the HUD rebuilds cleanly with no duplicate stacking. Three clone kinds: 7 score-digit clones and 7 high-score-digit clones (places 0-6, units to millions), each recomputing `floor(value / 10^place) mod 10` every tick and switching to `digit/<n>` by name; and a row of `life/ship` clones for the remaining craft, spawned by a shared `hud spawn craft` warp block called both at the initial spawn and again whenever `craft changed` fires — the rendered count is capped at `HUD_LIFE_MAX` (9) so the row stays on-screen while the true `craft` count keeps rising. Two label clone groups use static costumes fixed at spawn (inherited by the clone, like position): "HIGH SCORE" — rendered in the arcade's **yellow** from the `hs/*` glyph set (H,I,G,H, a skipped slot for the space, S,C,O,R,E) — and a flashing white "1UP" (glyphs 1,U,P) that loops show/hide while the HUD is visible. The glyphs are recolored at extraction (`tools/hud_glyphs.py`): white for the score, high score, 1UP, and GAME OVER, and yellow only for the HIGH SCORE label, matching the operator's arcade reference. All positions are a project-defined top-band layout (score group upper-left, high-score group upper-center, life icons and labels arranged around them) — the operator fine-tunes exact placement at playtest.
- Scratch evidence: `hud_blocks`, `install_hud_spawn_craft`, and the `HUD_*` role/position constants in `tools/game_director.py`; the generated `hud` target's blocks in `src/xevious/project.json` (clone spawning, `control_start_as_clone` role dispatch, the `craft changed` receiver). New `Blocks` helper methods this commit needed: `go_expr`, `switch_costume_expr`, `op_join`, `not_either_state`/`if_not_either_state`, and `if_var_equals`, added as siblings of the existing `go`/`switch_costume`/`op_*`/`either_state`/`var_equals` methods. Contract and negative-fixture checks in `tests/test_scratch_project.py`: `_eco02_failures` (clone spawning and dispatch present, the score/high-score digit costume-switch expression chain, the `craft`/`craft changed` wiring, the flashing 1UP loop, and the hud-writes-only-local-vars invariant) with its eight negatives; `test_hud_target_carries_expected_glyph_and_life_costumes` in `tests/test_hud_glyphs.py` was narrowed to drop its now-superseded empty-blocks assertion (that target's blocks were always documented as ECO-02's territory, per docs/mechanics/010).
- Acceptance criteria: `python3 tools/game_director.py check`, `python3 tools/hud_glyphs.py check` (24 costumes, untouched by this commit), `python3 tools/sprite_extractor.py check`, and `python3 tools/scratch_project.py verify` all pass; the HUD structural tests pass with their negatives. Operator playtest: pressing the debug **S** key climbs the score and the HUD digits roll in sync, the high-score readout tracks whenever the score passes it, and a bonus life grant (crossing the threshold) adds a life icon to the row.
- Fidelity status: Digit and high-score readouts, the craft row, and the two labels this slice specifies (1UP, HIGH SCORE) are implemented and operator-verifiable now via the existing debug **S** fixture. GAME OVER and 2UP are explicitly out of scope this commit (deferred to ECO-04 and a later commit respectively, per the HUD-render task boundary). No HUD element persists to disk.
- License status: No new reference material is transferred; the glyph costumes this commit renders were already ingested and licensed in docs/mechanics/010 (CC BY 3.0 font sheet; no-reusable-license-specified life icon and extend sound, both inheriting the existing Solvalou-sheet and Sounds-Spriters-Resource provenance).
- Known deviations or uncertainty: *(Positions superseded by slice 20, [record 054](054-arcade-screen-proportions.md): every HUD element now sits on the arcade text-layer cell the reference draws it on — labels row 0, scores row 1, life icons row 35 from column 4 — and the rendered life-icon cap is 28, the screen width.)* **Exact on-screen positions are a project choice** — the top-band layout (score upper-left, high score upper-center, labels above their groups, life icons in their own row) has no reference-pinned coordinates this commit; the operator adjusts spacing/placement at playtest. **The reserve-vs-total life-count convention is unresolved** — the row shows one icon per live `craft` (capped at 9 rendered), and whether the arcade HUD displays "reserve craft" (excluding the one in play) versus a raw total is not pinned here. Resolution step for the playtest: compare the icon count against the arcade reference at a known craft count (e.g. right after the first bonus award, when `craft` is 4) — if the arcade shows one fewer, switch the spawn count to `craft - 1`; the HUD_LIFE_MAX cap and the arcade's own displayed maximum should be reconciled at the same time. The 1UP flash cadence (`HUD_1UP_FLASH_HOLD_TICKS` = 15 ticks each way) is a project-defined placeholder with no reference basis. *Resolved in slice 21 ([record 056](056-release-fidelity.md) item 11): the label flashes 16 frames each way on the game clock, as `flash_1up_2up` does.* GAME OVER and 2UP labels, and the initials-entry screen, are explicitly deferred to later commits.

## Slice 18 — 2UP HUD (two-player)

The 2UP indicator deferred above (with two-player, CAB-03) is delivered this slice, completing
`ECO-02.two-player` (roadmap leaf `economy.two-player-hud`, closes #99).

- Behavior: in a two-player game the HUD adds the other player's **frozen** second score row (their
  score as it stood at their last swap-out) and a steady **"2UP"** label, alongside the active player's
  existing flashing **"1UP"** label. Each `nUP` label reads the current player, so after an alternation
  the labels flip (the newly-active player's label leads, the other's steady label names the other
  player). Both extra elements spawn **only** when `two player == 1`, so a one-player HUD is byte-unchanged.
- Reference provenance: `jotd666/xevious@71473685a8c7856c8401c8519276cd97a38d4183`. `src/xevious_sub.68k`: `sub_fn_6__display_1UP_2UP` (737–756) draws the 1UP/2UP labels, `flash_1up_2up` (769–777) flashes the label gated on a real game, and `up_string_tbl` (778–781) is the label string table; `src/xevious_ram.68k`: `is_real_game` (134) is the flash gate; `src/xevious_main.68k`: `display_player_scores` (1888–1901) draws the other player's score **only** when the game is two-player, frozen at their last swap-out.
- Scratch interpretation: two new clone roles on the `hud` sprite — an other-score digit role (7 clones reading the `other score` Stage variable through the same `floor(value / 10^place) mod 10 → digit/<n>` chain the live score uses) and a 2UP-label role (reusing `digit/2` + `glyph/U` + `glyph/P`). Both spawn inside an `if two player == 1` gate. Each label's leading glyph is computed from `curr player` (`digit/(curr+1)` for the primary label, `digit/(2−curr)` for the secondary), so the labels follow the active player. The HUD rebuilds every transition (`director stop` clears clones, `director enter` respawns), and `curr player` is toggled before the respawn transition, so the labels are snapshotted correctly at spawn.
- **Deliberate divergence — active-always-primary vs the arcade's fixed per-player columns.** The arcade keeps each player's `nUP` label and score in a **fixed screen column** (player 1 left, player 2 right) and flashes whichever player is currently active *in place* (`flash_1up_2up` 769–777, gated on `is_real_game` 134), drawing the other player's score only in a two-player game (`display_player_scores` 1888–1901). The port instead always draws the **active** player as the primary (flashing) label and score and the **other** player as the steady secondary — the drawn column follows `curr player` rather than the player index. This was the approved plan's riskiest-seam simplification (#5): it preserves the load-bearing behavior the reference specifies (active flashes, other steady, second row only in a two-player game, other score frozen at swap-out) while dropping the fixed-column placement, which is a HUD-layout choice the operator tunes at playtest and which the headless harness cannot observe. Reference-fidelity reviewed and the operator approved keeping this divergence.
- Scratch evidence: `HUD_ROLE_OTHER_SCORE_DIGIT`, `HUD_ROLE_LABEL_2UP`, their columns, and the `up_label_spawn` helper + the two-player-gated secondary group in `tools/game_director.py`; the generated roles/costumes in `src/xevious/project.json`; extended `_eco02_failures` checks in `tests/test_scratch_project.py` (the `other score` digit costume chain, both new role dispatches, and the two-player gate) with a biting negative each, plus the re-pinned build hash; harness `two-player-hud-render` (2P draws both rows + correct labels; 1P draws neither) and `two-player-clone-no-leak` (2P peak clone census stays under the scratch-vm ceiling with ≥50 headroom, returns to baseline across two alternations, and the active label tracks the current player) in `harness/lib/catalog.js`, each with a biting negative.
- Known deviation carried forward: exact on-screen column placement of the two-player rows/labels stays a project layout choice the operator fine-tunes at playtest (as with the one-player HUD above), and is the visible half of the active-primary divergence.

## Correction (area-clock slice — life-icon crop)

Operator playtest caught the `life/ship` icon rendering as a Solvalou *explosion* burst rather than
the intact ship: the `life_icon.rect` in `assets/hud-font/manifest.json` was `[138, 28, 16, 16]`, a
round explosion frame on the Solvalou sheet, not a ship frame. Corrected to `[5, 27, 16, 16]` — the
forward flight frame (identical crop to `solvalou/flight/01`). Because the pixels are byte-identical,
the rendered life icon dedups to the already-extracted flight-frame asset (`30ace72a…`, now shared by
`solvalou/flight/01` and `hud:life/ship`), so the overlay asset count drops by one (99→98) and the old
unique explosion asset is removed. `tools/hud_glyphs.py` was hardened so that when the life icon dedups
to an asset already referenced by a non-HUD costume, it **defers to that asset's existing (sprite
extractor) provenance record** instead of clobbering it — keyed off the project's costume references so
it stays idempotent. The regression test `life-ship-costume` only asserts the clones *switch to*
`life/ship`; it cannot see the costume's pixels (the headless harness renders nothing), which is why a
wrong crop passed every automated gate and only the operator's eyes caught it — the class of
visually-wrong-but-structurally-present defect the playtest exists for.
