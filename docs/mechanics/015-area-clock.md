# Area scroll clock, the 16→7 area loop, and the near-end death checkpoint

- Mechanic: AREA-01 — one monotonic scroll position advanced each tick before the object walk and carried from area to area within a life; it completes an area at scroll row 0x0E, advances the area number with the 16→7 loop, (discharging the obligation deferred by PLY-02) applies the near-end checkpoint to the death reset scope, and (slice 20) drives the visual terrain, rendered from the arcade map.
- Derived behavior: One scroll clock moves continuously through the game, set to the area top only when a life begins. When the clock's high byte (the "scroll row") reaches 0x0E the area completes: the area number increments, and completing area 16 continues at area 7 (not area 1, no win screen); the clock keeps running, so the new area's map rows simply start arriving. Every new life restarts the current area from its top — except a death in roughly the final fifth of an area (scroll row 0x0E–0x43, read after the death's explosion) advances to the next area instead. A new game starts at area 1. The terrain is the arcade's own map, at the area's map column, scrolled by the clock.

- Scratch interpretation: The sole position authority is `area progress`, a Stage variable stepped by 32 per build tick (16 counter units/arcade frame × 2 frames/tick). **Slice-20 shape (supersedes the slice-5 re-top at completion described below):** completion requires row 0x0E **and** `area progress` > 0 (the arcade's two-phase wait), and changes `area progress` by −65536 (65056 → −480: the same counter value, still row 0x0E) instead of setting it to 0, so the clock carries on into the next area and the guard keeps the 8 carry ticks on row 0x0E from completing it again. `_enter_area_top` is split along the source routines: `_enter_next_area` (terrain column, previous terrain column, schedule cursor, fired flag) runs at completion and at every re-top; only the re-top (cold start, new game, new life) also sets `area progress` to 0, snaps the row and clears the wave registers. Area 1 therefore lasts 2033 ticks and every area reached by completion 2048. The position is still monotonic within a life; the −65536 is a change of origin paired with the area number advancing, not a rewind. The arcade scroll row is DERIVED once per tick into `scroll row` = `floor(((0x0D00 − area progress) mod 0x10000) / 256)` (built through the centralized operator helpers, so the operand slot keys cannot silently drift to NaN); because 256 is divisible by 32, every row is visited and no schedule trigger is skipped. A new warp block `advance area` runs from the walk thread BEFORE `advance slots`, matching the reference frame order (`handle_next_area` → `handle_objects` → object updates); on the first tick `scroll row` reaches 0x0E it advances the area (a shared 16→7 helper), re-tops `area progress`, and sets the per-area `terrain column` — completion and (AREA-02's) schedule consume are the two arms of one `if/else`, so they never both run on a boundary tick. The near-end checkpoint lives in a SEPARATE Stage `director reset` receiver `area_reset` (kept off `stage_reset`'s pinned opcode chain, like the eight existing reset receivers): on cold-start/new-game it returns to area 1 and re-tops; on a new life, if the frozen scroll row is in [0x0E, 0x43] it advances the area with the same 16→7 helper, then re-tops. On a scope-`none` transition (the death itself) and on game-over it does nothing, so `area progress`/`scroll row` stay frozen through the death sequence. **Slice 20 (owner decision: match the outcome):** the arcade keeps scrolling through the 88-frame explosion and pause, with completion live, and reads the row only then; the port keeps its frozen screen but one shared warp proc `_area_checkpoint` (used by the new-life re-top and the two-player handoff) projects the death-tick progress 44 ticks ahead into a new Stage machinery variable `checkpoint progress`, completes the area first if that passes 65056 (carrying by −65536), then applies the arcade's test (row − 14 < 54, i.e. [0x0E, 0x43]) to the projected row. The band therefore begins at death-tick progress 50080; a death 37–44 ticks before the end skips the next area too; a death in the carry window restarts the new area. The handoff puts the clock at the area top after the swap, so the incoming player's re-top projects from row 7 and leaves their area alone.

  **Terrain (slice 20).** `tools/terrain_render.py` decodes the map ROMs and background tiles at the pin into a committed master map (`assets/terrain/arcade_map.png`, 1024×2048, 1 px per arcade px) and the forest filler, proved against the reference's video-memory snapshot (38 rows at area 9, column 42), and slices them into six costumes: four 64-row bands (plus 2 overlap rows on top), band 3 with its never-written row 255 transparent (for re-tops), and the filler. The two existing strips keep their names: `area_01a` shows the even bands and the filler, `area_01b` the odd bands and the restart band. A Stage warp proc `update terrain` computes each strip's costume, x, y, shown flag and which strip is in front as a pure function of `area progress`, `terrain column` and `previous terrain column` (−1 = filler after a re-top; the outgoing column after a completion, which band 0 keeps while the old area's last rows are on screen). The walk runs it after the clock and the ground objects move, every re-top runs it last, and each broadcasts `terrain draw`, on which a strip only switches costume, goes to x/y, shows or hides, goes to back, and comes forward one layer if it holds the upper band. Size 125 is set only in the target records (scratch-vm caps a block-set size at 1.5× the stage). The phase between the map and the ground sprites is derived from the reference renderer's terms (they cancel to 0) and pinned as named constants, so an object scheduled at row S rides the top edge of map row S − 2 on every tick, matching the arcade.
