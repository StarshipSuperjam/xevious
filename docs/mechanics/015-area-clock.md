# Area scroll clock, the 16→7 area loop, and the near-end death checkpoint

- Mechanic: AREA-01 (partial, foundation) — one monotonic per-area scroll position advanced each tick before the object walk; it completes an area at scroll row 0x0E, advances the area number with the 16→7 loop, and (discharging the obligation deferred by PLY-02) applies the near-end checkpoint to the death reset scope.
- Derived behavior: Each area runs a scroll clock that moves continuously through the area. When the clock's high byte (the "scroll row") reaches 0x0E the area completes: the area number increments, and completing area 16 continues at area 7 (not area 1, no win screen). Every new life restarts the current area from its top — except a death in roughly the final fifth of an area (scroll row 0x0E–0x43) advances to the next area instead. A new game starts at area 1.

- Transfer class: General behavior and numeric constant.
- Scratch interpretation: The sole position authority is `area progress`, a monotonic INCREASING Stage variable stepped by 32 per build tick (16 counter units/arcade frame × 2 frames/tick), so "position never rewinds during a life" is a one-line invariant. The arcade scroll row is DERIVED once per tick into `scroll row` = `floor(((0x0D00 − area progress) mod 0x10000) / 256)` (built through the centralized operator helpers, so the operand slot keys cannot silently drift to NaN); because 256 is divisible by 32, every row is visited and no schedule trigger is skipped. A new warp block `advance area` runs from the walk thread BEFORE `advance slots`, matching the reference frame order (`handle_next_area` → `handle_objects` → object updates); on the first tick `scroll row` reaches 0x0E it advances the area (a shared 16→7 helper), re-tops `area progress`, and sets the per-area `terrain column` — completion and (AREA-02's) schedule consume are the two arms of one `if/else`, so they never both run on a boundary tick. The near-end checkpoint lives in a SEPARATE Stage `director reset` receiver `area_reset` (kept off `stage_reset`'s pinned opcode chain, like the eight existing reset receivers): on cold-start/new-game it returns to area 1 and re-tops; on a new life, if the frozen scroll row is in [0x0E, 0x43] it advances the area with the same 16→7 helper, then re-tops. On a scope-`none` transition (the death itself) and on game-over it does nothing, so `area progress`/`scroll row` stay frozen through the death sequence and the checkpoint reads the real death-tick row. The visual terrain strips stay DECOUPLED from the clock this slice (only area-1 art exists); `terrain column` is a dormant seam consumed when the presentation slice (20) couples them.

- Known deviations or uncertainty: `advance area` before `advance slots` locks the PHASE order the enemy slices inherit, not a random-stream draw sequence — no phase draws from the RNG this slice (both dispatch bodies are empty), so the lock is verified structurally, not behaviorally. Completion fires at the first tick the row reaches 0x0E, which is `area progress` 65056 (≈2033 ticks), not the 0xFF00/65280 figure the spec cites as the counter span; the mechanism is row-driven and correct. The row-14 edge of the checkpoint window is a vacuous runtime state (completion resets the area before a death can be observed at row 14), so the reachable checkpoint floor at death is row 15; the boundary logic still handles 14 and is tested there. The visual terrain scroll and the clock are two independent authorities this slice and could drift; reconciliation is time-boxed to slice 20.
