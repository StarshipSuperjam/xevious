# Two-player alternation, independent player state, and the 1P/2P start selector

- Mechanic: CAB-03 (two-player alternation) with the CAB-02 two-player start facet (`CAB-02.two-player`) — strict alternating two-player play: two players share one cabinet, each with a fully independent game (score, remaining craft, area, difficulty, bonus-life state), and control hands off to the other player on **every** craft death while that player still has craft. A credit-gated title selector chooses one- or two-player before the start, and a brief "GAME OVER PLAYER n" banner marks the handoff when one player is eliminated but the other is still in. Initials **entry** for a qualifying player is CAB-04 (slice 19) and stays out of scope; this record computes only the per-game `qualified` verdict, once, at the final game-over — exactly as the one-player path did.
- Derived behavior: The arcade reads coins and the start buttons in one routine and starts only an affordable requested mode — one player needs one credit, two players need two — deducting the cost and recording the mode as `two_player_game` (0 = one player, 1 = two players). On a two-player start the current player is forced to player 1, a fresh player-1 context is built, and that fresh block is copied into the other-player block so player 2 starts identical-fresh. During play the active player's state lives in one 64-byte block; on a craft death, if the current player still has craft **and** the other player still has craft, the two blocks are exchanged and the current-player index is toggled, so the *other* player takes the next turn; if the other player is out, the current player continues solo; when the current player is eliminated (out of craft) but the other still has craft, control hands to the survivor after a brief game-over banner; when both are out the game ends and the current-player index is forced back to player 1. The pseudo-random seed sits **outside** the per-player block and is never swapped — both players draw from one shared, deterministic stream — while each player's area, AI level, and fire masks travel with them inside the block.

- Scratch interpretation: The port keeps its existing active gameplay variables as the **current** player and adds one `other <x>` shadow variable per persistent per-player field, faithful to `swap_curr_other_player`. The swap set is 14 fields — `score`, `craft`, `next bonus`, `area number`, `ai level`, `ground stop firing row`, and the eight per-family fire masks — each exchanged by a `swap players` custom block through a `swap tmp` register; a `copy players` block copies the current block into the other block for the two-player start. Gameplay, HUD, and spawn code (which read `score`, `craft`, `area number`, … and are pinned Stage-write-only by the write-forbid guard) are untouched; only start, death, game-over, the HUD, and the swap/copy blocks see the shadow block. `curr player` (0/1) and `two player` (0/1) join the director state names; `swap tmp`, `start selection` (1/2), and `banner player` (0/1/none) are machinery. The pseudo-random seed (`rng state`), `high score`, `credits`, the DIP flag, and the per-game `qualified` verdict stay global and are never swapped. Because the arcade has no cabinet start buttons, the port's title **selector** is a port necessity like the `C` coin key: left/right arrows choose one- or two-player at the title, Space confirms and starts the affordable requested mode (one player needs ≥1 credit and deducts one; two needs ≥2 and deducts two; insufficient credits is a silent no-op). `curr player`, `two player`, and `start selection` reset only at cold-start (never new-game), so a two-player start's `two player = 1` is not clobbered and a finished game returns to player 1 / one-player. On a craft death the `death complete` handler tries the alternate path first (`two player == 1` and `other craft > 0`): it applies the outgoing player's end-of-area checkpoint to *their own* area number **before** the swap, raises the banner if the outgoing player is now eliminated, calls `swap players`, toggles `curr player`, resets `scroll row` to the area-top row so the incoming re-top does not re-run the checkpoint, and runs the respawning/new-life transition that re-tops the **incoming** player's area; otherwise it falls through to the existing one-player respawn-or-game-over branch. The formation registers (`formation count`, `formation type offset`) are **not** swapped — they are zeroed in `_enter_area_top` on every area entry (mirroring the existing bacura/sheonite re-clears), matching the arcade's life-start clear; the derived area state (progress, scroll row, terrain column, schedule cursor) is likewise rebuilt from the area number rather than carried. The RNG seed is reseeded only under the cold-start/new-game guard, so alternation (which uses respawning/new-life) never reseeds and a two-player game is deterministic from one shared stream.

- Known deviations or uncertainty: (1) **Port necessity — title 1P/2P selector.** The arcade used two dedicated start buttons and chose its "1 PLAYER ONLY / 1 OR 2 PLAYERS" prompt by credit count; with no cabinet buttons the port maps the choice to the title left/right arrows plus Space, a permanent control-mapping addition recorded in the locked control-mapping spec (`docs/spec/core-game-systems.md`). (2) **Formation registers zeroed on re-top, not swapped.** The arcade clears `num_flying_enemies`/`flying_enemy_type_tbl_offset` at every life-start (`main_gameplay_loop` 484–485) and rebuilds them from `enemy_AI_level`; the port has no distinct swapped port variable for them and zeroes the equivalent `formation count`/`formation type offset` in `_enter_area_top`, which runs on every area entry (1P new-life and area-advance included) — an arcade-faithful clear of transient wave state, not a swap-only change. (3) **Two arcade block fields have no distinct port variable** — `solvalou_number` (the per-death score divisor for AI re-tuning) is carried by `craft` under the port's DIF-02 `score / craft` formulation, and `bonus_life_none` (bonuses-off DIP) is encoded as the sentinel `BONUS_DISABLED` inside `next bonus`; both are covered by fields already in the swap set, so no state leaks between players.
