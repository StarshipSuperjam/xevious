# Exact reference values are captured in the spec, once, by tool

## The decision

The product specification records the exact numeric values of the arcade game — scores, timings, difficulty
increments, formation data, and all sixteen area schedules — extracted from the pinned reference commit. Bulk
tables are transcribed exactly once, into machine-readable files under `docs/spec/data/` generated by a
committed extractor whose decode must consume every source table exactly or fail; capability documents
describe the meaning of that data and hold only scalar values inline, each with a file, label, and line-range
citation.

## Why

The project exists because a build session invented gameplay with no basis in the arcade game, and a spec
that says "fast" where the arcade has a number leaves that door open. Exact values make divergence checkable:
a reviewer can follow any citation to the pinned commit and falsify the claim. The tool-generated single
transcription answers the two failure modes hand-copied values would create — a plausible-but-wrong decode of
the reference's undocumented variable-length byte streams (the extractor's exact-consumption proof catches a
mis-sized record anywhere in a table), and silent drift between the numbers the spec states and the numbers a
build ships (both consume the same committed files). The cost — a deliberate widening of the recorded
reference boundary to allow committed derived data — was accepted by the operator and recorded in
`docs/REFERENCE_POLICY.md` under the guardrail acknowledgement.

## What we ruled out

- **Behavior descriptions with citations only, values extracted at build time.** The strongest alternative:
  lighter to author and no boundary widening. It lost because every build session would re-extract values
  independently, reproducing exactly the unverifiable-transcription risk this effort exists to remove, and
  the spec could never be checked against the reference without redoing the whole extraction.
- **A hybrid — exact values for small tables, citations only for the sixteen area schedules.** It lost
  because the schedules are the data most likely to be improvised (they are the game's content), and the
  extractor made full extraction cheap: all sixteen tables total 3.6 KB and decode with a completeness
  proof.
- **Hand-transcribed tables in the capability documents' prose.** It lost on evidence: a one-character hash
  transcription error occurred during this very intake and was caught only by mechanical comparison. Prose
  tables would also be a second copy the moment a build turned them into Scratch lists.
