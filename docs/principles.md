# Product principles

## What this product is for

A faithful, playable Scratch 3 interpretation of the normal Namco arcade release of Xevious, built for the
project owner to play and share. Faithfulness means the game a player experiences — enemies, schedules,
scoring, difficulty, and flow — matches the arcade original wherever Scratch can express it, and every
departure is recorded rather than improvised. Every principle below serves that outcome.

## Principles

- **The arcade original is authoritative.** The normal Namco arcade release defines correct behavior; later
  ports and Super Xevious additions are excluded. When sources disagree, the arcade wins. This rules out
  borrowing convenient behavior from home ports or inventing modern conveniences the cabinet never had.
- **Every gameplay behavior is traceable or it does not ship.** A behavior in the built game must carry one
  of exactly four markers: a citation to the pinned reference (commit, file, label, line range), a recorded
  *deliberate deviation* with its reason, a recorded *port necessity* where Scratch cannot express the
  original, or *preserved baseline behavior pending a fidelity pass* — proven 2017-baseline behavior kept
  until the arcade value is extracted, retired the moment it is. A behavior with none of the four is a
  defect — the failure this project exists to prevent.
- **Preserved baseline behavior may not be removed silently.** Behavior proven in the preserved 2017 baseline
  or in a previously merged slice is load-bearing. Removing or replacing it requires an explicit recorded
  decision in the change that does it. Silence means preserve. This is the rule the project's worst incident
  violated; it exists so that incident cannot repeat quietly.
- **No pull request is ready until the owner has played it.** Every change that can affect gameplay produces
  a playable `.sb3` built from the final reviewed commit, with a list of behavior added or changed. The pull
  request stays draft until the owner has run [the playtest checklist](PLAYTEST_CHECKLIST.md) on that build
  and approved it. Automated checks in this
  repository read files; none of them can observe a running game, so the owner's playtest is the only
  gameplay verification that exists.
- **New and preserved behavior are tested together.** A change's acceptance list covers what it adds *and*
  everything it could disturb: held-input and duration interactions (holding fire while moving, multiple
  terrain cycles, repeated deaths), not just single key taps — with negative fixtures proving the tests
  can fail. Wholesale replacement of a working script is
  high-risk and requires behavior-by-behavior comparison against what it replaces. An unverified runtime
  finding stays open — it is never converted into a promise and waved through.
- **Every value has exactly one normative home.** A number (a score, a speed, a schedule entry) is stated
  with its value and citation in one document or data file; everywhere else names it and links. Two
  statements of the same value is how contradictions are born.
- **Bulk reference data is transcribed once, by tool.** Schedules, formations, and tables live as committed
  machine-readable files generated by the deterministic extractor, which must consume each source table
  exactly or fail. The spec describes their meaning; builds generate Scratch data from the same files. No
  hand copy of a table is ever authoritative.
- **Transcode-derived is not arcade-confirmed.** Every extracted value derives from a reverse-engineered
  transcode that itself acknowledges one unidentified remaining gameplay divergence from the arcade. No
  value in this spec is claimed as arcade-confirmed; observing the arcade remains the only confirmation
  path, applied selectively where fidelity doubts matter most.
- **Honest verification accounting.** Acceptance criteria name who can actually check them. "Engine-checked"
  is reserved for what a repository script genuinely decides — structure, provenance, data contents,
  determinism. Observable gameplay is always the owner's to confirm on screen, and the split is reported
  plainly before anything is settled.
- **Provenance discipline, no rights claimed.** The reference states no reusable license; this project
  records that honestly, claims no rights in Namco's trademarks, artwork, or audio, copies no assembly or
  other source text, and never acquires or opens arcade ROM files. A rights review is required before any
  broader distribution or promotion.

## What these rule out

- Inventing gameplay dynamics, timings, or presentation with no basis in the reference and no recorded
  deviation marker — however plausible they feel.
- Removing or degrading working behavior as a side effect of refactoring, without a recorded decision.
- Calling a pull request ready before the owner's playtest of the built `.sb3`.
- Copying assembly text, ROM contents, or the reference's own prose into this repository.
- A second hand-maintained copy of any reference table, in docs or in Scratch data.
- Acceptance rows that claim machine verification of on-screen behavior this repository cannot observe.
- Treating Super Xevious content, port conveniences (pause, persistent high scores), or a conventional win
  screen as in scope — area 16 loops back to area 7; that is the arcade's ending.
